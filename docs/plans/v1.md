Written 2026-10-20. Covers both workstreams: [assembly-tools.md](assembly-tools.md) (MCP tools) and [knowledge-base.md](knowledge-base.md) (RAG). Status lives in `Status.md`.

## The goal

**Claude designs and builds a complete BIOBUZZ robot in Fusion, one subsystem at a time, as the user asks for each: "let's work on the shooter", then the drivetrain, then the transfer, then the intake. It uses real goBILDA parts plus custom laser-cut and printed parts, and only MCP tools and the knowledge base. The user writes each brief, picks between concepts, and gives verdicts. When asked, Claude can also run every subsystem by itself in one go.**

## How the work flows

### The robot design file
Subsystems are built in different sessions, so one file carries what they agree on: `kb/designs/<robot>/design.md`. Claude reads it at the start of every subsystem session and updates it at the end.
- **Robot frame of reference:** origin, front, up.
- **Per subsystem:** its **envelope** (a box in robot coordinates), its **interfaces** (where it mounts: holes, shafts, plates, and who provides them), its **actuator budget** (its share of the 8 motors and 8 servos), its status (not started / concept / built / accepted), and links to the KB entries it was based on.
- **Open questions** between subsystems ("the transfer needs to hand balls to the shooter at about z = 30 cm").

In Fusion, the robot is **one document** with **one top-level component per subsystem** (Drivetrain, Intake, Transfer, Shooter, Turret). A subsystem session works only inside its own component, and a transparent envelope box shows its space.

### Robot kickoff (once per robot, before the first subsystem)
Claude creates the design file (`robot_design` action `create`) and proposes, for every planned subsystem, its **envelope** (stowed, plus an `extended` box for anything that moves out) and its **actuator budget**, with the totals at ≤ 8 motors and ≤ 8 servos. **The user approves or edits the split.** Later sessions build inside it; changing a budget or envelope is a design-file update the user agrees to. Coordinates: origin at the centre of the footprint on the tiles, +x right, +y front, +z up, in cm.

### One subsystem session ("let's work on the shooter")
1. **Load:** open the robot document and read the design file, `design_rules.md`, `lessons.md` and the game constraints.
2. **Brief:** the user says what it needs and what to watch out for, and can point at an old version.
3. **Research:** `kb_search` / `kb_get` for similar mechanisms and ideas, ranked by team rating and past verdicts.
4. **Concepts:** Claude proposes 2–3 with key numbers and trade-offs. **The user picks.**
5. **Build** inside the subsystem's component: goBILDA parts with `kb_find_part` → `insert_part` → `join_on_holes`, custom parts modeled to `design_rules.md`.
6. **Subsystem checks:** fits its envelope, no interference with subsystems already built, within its actuator budget, joints healthy, moves through its range (`set_joint_value`).
7. **Verdict:** the user accepts or sends it back. `kb_feedback` records which KB entries the verdict applies to.
8. **Save:** save the Fusion document, update the design file (status, actual interfaces, BOM), and `kb_save_design` the accepted subsystem as our own mechanism card.

**Order:** the user chooses. Usually the drivetrain comes first because the others mount to it. If a subsystem is built before the part it mounts to, its interface is taken from the design file and checked when the other part is built.

**"Do it all":** Claude runs the same loop for every subsystem in order. It stops for concept picks unless the user says to choose for them, and it reports every check result.

## The first-robot test (v1 is done when this passes)

Built subsystem by subsystem as above: drivetrain, intake (POLLEN), transfer, shooter (a turret is optional), in whatever order the user picks.

**Each subsystem must pass:** S1 fits its envelope · S2 no interference with built neighbours · S3 within its actuator budget · S4 joints healthy and moves through its range · S5 the user accepted it · S6 verdict recorded with `kb_feedback` · S7 saved (`kb_save_design`, design file updated).

**The finished robot must pass:**

| # | Criterion | Checked by |
|---|---|---|
| P1 | Starting configuration fits the 18 in cube (R102) | `check_robot_rules` |
| P2 | Fully extended, it fits 18 × 24 × 29 in (R105) | `set_joint_value` to max + `check_robot_rules` |
| P3 | ≤ 8 motors and ≤ 8 servos in total (R503) | `check_robot_rules` (from `get_bom`) |
| P4 | No interference anywhere in the stowed position | `check_interference` |
| P5 | Every joint healthy | `list_joints` |
| P6 | COTS parts are real goBILDA STEP parts; custom parts follow `design_rules.md` | `get_bom` + review |
| P7 | **Zero `execute_code` calls** across all sessions | session tool logs |
| P8 | The user wrote no CAD | session logs |

**Recorded (not pass/fail):** per subsystem, the tool calls, errors, wall time, sessions and send-backs. That's the baseline v2 improves on.

**The first subsystem is the rehearsal.** If it can't pass S1–S7, fix the gaps before building the next.

### Coordination rules
1. **Fusion has one driver at a time.** Lanes A and C both need it. The driver is named at the top of `Status.md` ("Fusion: Lane A") and cleared when done. Big STEP imports (Lane C) block Fusion for up to 75 s and can drop the MCP socket, so they never overlap with live tests (Lane A).
2. **Onshape calls: only Lane C.** It keeps the yearly log in `kb/ingest/api_calls.csv` (hard stop at 2,000).
3. **Files have one owner.** No one edits another lane's files. `command_handler.py`, `tools.py` and `mock.py` belong to Lane A until PR #1 is merged. `kb_tools.py` and `server.py` are shared by D and F; each adds only its own tool, prompt or resource, and the coordinator merges them.
4. **Every lane** runs `uv run pytest` and `uv run ruff check` before handing over, updates its own section of `Status.md` (exact-text edits only), and adds lessons a future session needs to "Learned Lessons" in `Claude.md`.
5. **Merging into `main`** is done by the coordinator: PR #1 (Lane A) via GitHub review, then D, F and E. Each merge needs the user's OK until the user says otherwise.

### What only the user can do
- Review robot drafts (Lane C's speed is set by this).
- Give `design_rules.md` its real numbers: printer hole tolerance, bearing pocket fit, laser kerf for wood and aluminum, plate thicknesses, the aluminum laser service's limits.
- Review and merge PR #1 on GitHub.
- Write the first-robot brief, pick concepts, and give verdicts during the test.
